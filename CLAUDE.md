# Patrol Station

A database-per-tenant multi-tenant SaaS for managing fuel stations (fuel inventory, pumps, cash box, debts, Sadcop supplier ledger, shop items). Sold to station owners, onboarded manually — no self-serve signup.

**Stack:** Laravel 13, Inertia v3 (`@inertiajs/react`), React 19, TypeScript, Tailwind v4, Vite, `stancl/tenancy` v3.10, Spatie `laravel-permission`, Wayfinder (typed route helpers).

**Production:** Fly.io app `patrol-station` — https://patrol-station.fly.dev. Deploy with `fly deploy -a patrol-station`.

## Multi-tenancy

- **Database-per-tenant**: one SQLite file per station. Tenant migrations live in `database/migrations/tenant/`; central migrations (tenants, tenant_user_directory, central users for the platform super admin) stay in the normal `database/migrations/` path.
- `app/Tenancy/SqliteDatabaseManager.php` resolves tenant DB file paths via `config('tenancy.database.sqlite_path')` (points at the persistent Fly volume `/data` in production, `database/` locally).
- Tenant identification is **login-based**, not domain-based: one URL for everyone. `session('tenant_id')` + `InitializeTenancyFromSession` middleware re-initializes tenant context every request. Fortify's `authenticateUsing` checks the central `tenant_user_directory` first, then switches into that tenant's DB to verify the password.
- Middlewares: `RequireTenant` (redirects super admins away from tenant routes), `RequireSuperAdmin` (mirror, for `/platform/*`), `RequireOnboarding` (gates operational routes behind the first-run wizard until `tenant('onboarded_at')` is set), `ForcePasswordChange` (temp-password flow for freshly provisioned stations).
- `FilesystemTenancyBootstrapper` is **deliberately not registered** in `config/tenancy.php` — this app never stores per-tenant files, and that bootstrapper rewrites Vite asset URLs, which broke the production JS/CSS bundle. Don't re-add it.
- Admin (`admin/*`) routes are intentionally *not* gated by `RequireOnboarding` — the wizard only collects opening balances; tanks/pumps/fuel types are set up through the normal admin CRUD first.

## Arabic / i18n — read this before adding any user-facing string

- **Backend**: `lang/ar.json` is a Laravel JSON translation file. Every `__('Some string')` call in PHP needs a matching entry here or it silently falls back to raw English in Arabic mode — there is no other Arabic translation source for backend strings. PDF exports use a separate, parallel pattern: inline `app()->getLocale() === 'ar' ? [...] : [...]` arrays per controller (do not try to route those through `__()`).
- **Frontend**: `t()` from `useTranslation()` (`resources/js/lib/i18n.ts`) reads the same `lang/*.json` files as the backend, in 11 languages (en, ar, fr, es, de, it, tr, ru, ur, hi, ku); a key missing from any of them fails `LocalesTest`. Its type is generated from `en.json`, so a key used in TS must exist there. `t(key, { name: value })` fills `:name` placeholders, like `__()`.
- **RTL**: use logical Tailwind classes (`start-`/`end-`/`ps-`/`pe-`), never physical (`left-`/`right-`/`pl-`/`pr-`) — physical classes don't flip in RTL and have caused visible layout bugs.
- `resources/js/lib/format.ts`'s `formatNumber`/`formatDate`/`formatDateTime`/`formatMoney`/`formatSyp`/`formatUsd` all force `'en-US'` explicitly, even in Arabic mode — otherwise a browser set to Arabic renders Arabic-Indic digits, which looks broken next to the rest of the UI.
- `html[dir='rtl']` gets a larger base `font-size` in `resources/css/app.css` (`@layer base`) — the Latin font has no Arabic glyphs, so the system fallback renders visibly smaller than the rest of the UI otherwise.

## Windows / Git-Bash environment gotchas

This project is developed on Windows via Git-Bash. Two real bugs came from this environment — watch for both:

1. **Arabic/UTF-8 text passed as an inline `curl` command-line argument gets silently corrupted to literal `?` characters.** Bash itself holds the correct UTF-8 bytes; the corruption happens in the OS-level argv hand-off to `curl.exe`. **Fix**: write the value to a temp file (a real Windows path, not `/tmp/...`) and pass it with `curl --data-urlencode "field@/path/to/file"` instead of `"field=$value"`. `php.exe` does **not** have this problem — its argv handling preserves UTF-8 correctly, so `php -r '...' "$arabicVar"` is safe.
2. `php -r` / `php artisan` print a harmless `Warning: PHP Startup: Unable to load dynamic library 'sodium'...` to **stdout** (not stderr) on this machine. This corrupts naive `$(php ...)` command substitutions — always pipe through `| tail -1` when capturing PHP output into a shell variable.

Other quirks:
- **`php artisan tinker <file>` waits for keyboard input once the script is done** unless its input is closed: run it as `... tinker file.php < /dev/null` (`scripts/dev/local-run.sh` does) — this was the "tinker hangs" seen before.
- Git Bash turns an argument like `/cash-box` into `C:/Program Files/Git/cash-box` (MSYS path conversion); `browser-check.mjs` undoes it, elsewhere prefix `MSYS_NO_PATHCONV=1`.
- Make code edits with the Edit tool, not `sed`/`node -e` one-liners: Git Bash strips backslashes (PHP namespaces) and mangles quotes in them.
- Node.js path resolution is unreliable for `/tmp/...`-style paths from the Bash tool. Copy files into `storage/app/` (a real path under the project) before running Node parsing scripts, then delete them afterward.
- Port 8000 is occupied by an unrelated local project — use another port (8001+) for `php artisan serve` during manual/smoke testing.
- Fetching an Inertia page via `curl` with `X-Inertia: true` but no matching `X-Inertia-Version` header gets a `409` conflict. Simplest fix: do a plain full-page GET (no `X-Inertia` header) and regex out the `<script data-page="app" type="application/json">...</script>` payload instead of trying to hit the partial-reload endpoint directly.
- `fly ssh sftp put <local> <remote>` mangles `/tmp/...`-style paths through Git-Bash's MSYS path conversion on **both** sides — prefix the command with `MSYS2_ARG_CONV_EXCL="*"` and use a real Windows path (e.g. `storage/app/<file>`) for the local side; the remote `/tmp/...` side is fine as-is once conversion is disabled.

## Debugging on the production container

- `fly ssh console` runs as **root**, not `www-data` (confirmed via `id`) — the actual web server (PHP-FPM) always runs as `www-data` (uid/gid 33, per the Dockerfile's `chown -R www-data:www-data storage bootstrap/cache`). **Never run a PHP script via `fly ssh console` that touches `storage/app/**` (or anything else the app writes to at runtime) without first dropping privileges** (`posix_setgid(33)` then `posix_setuid(33)`, while still uid 0) — a root-owned file/directory created this way blocks the real `www-data` process from writing there afterward with a confusing "not writable" error, indistinguishable at first glance from a real permissions bug in the app. (This exact mistake happened once: a debugging script created `storage/app/mpdf` as root, which then broke every real PDF export on the site until the directory was `rm -rf`'d and recreated by a privilege-dropped script.)
- To pull the real exception (not just the access-log line) for a 500 in production: `fly ssh console -a patrol-station -C "grep -a 'production.ERROR' /var/www/html/storage/logs/laravel.log"` — `fly logs` only shows the access-log line (`"GET /index.php" 500`) with no exception detail.
- A `fly ssh console` command's *own* stdout/stderr is genuine even though the process often ends with a spurious `Error: The handle is invalid.` on this Windows client — that trailing line is a PTY-cleanup artifact, not a sign the command itself failed.

## Checking levels — pick one per change, and tell the user which

Pick the level from what the change touches; **when unsure, use the higher one**, and name the level used in the report to the user. The scripts are in `scripts/dev/` (see its README).

| Level | When | Checks |
|---|---|---|
| **1 · UI only** | layout, colours, text, translations — nothing that computes, validates or stores | build (+ `tsc`, eslint, prettier on what changed) · `node scripts/dev/browser-check.mjs <pages>` at **1366px** · deploy (`scripts/dev/deploy.sh`) |
| **2 · Logic** | calculations, validation, flows, what a page shows from data — no schema or stored-data change | level 1 + `php artisan test` and `npm run test:js` (add tests for the change) · browser check of the changed flow · `scripts/dev/deploy.sh --smoke` (login 200 + `prod/smoke.php` on every station) |
| **3 · Data, money or migration** | a migration, anything that writes or rewrites stored data, money/stock/sales figures | level 2 + `scripts/dev/prod-backup.sh <label>` before deploying · local `scripts/dev/local-db.sh backup` before migrating locally (restore after testing) · before/after comparison: `prod/fingerprint.php` on production before the deploy and after, `fp-compare.php` must show every part identical (`FP_IGNORE` for what the change adds on purpose; if staff added records in between, compare old vs new code on the backup copy instead) · browser check at **1366, 1920 and 2560px** · read-only production check of what changed |

Every level, before committing:
1. `./vendor/bin/pint --dirty` (PHP changed), `npx tsc --noEmit`, `npx eslint <changed paths>`, `npx prettier --write <changed paths>`; PHPStan when PHP changed: `env -u CLAUDECODE -u CLAUDE_CODE_ENTRYPOINT -u AI_AGENT php -d memory_limit=2G vendor/bin/phpstan analyse`.
2. `php artisan test` healthy baseline: **137 tests, 129 passed, 8 skipped** (the skipped ones need Fortify features this app turns off: registration, two-factor). `npm run test:js` runs the frontend logic tests in `tests/js/` (Node's own test runner; keep what they import free of `@/` imports).
3. `npm run build`. After adding/changing a route: `php artisan wayfinder:generate --with-form`.
4. Translations: `php scripts/dev/add-keys.php keys.php` (all 11 languages; refuses to overwrite an existing key or remove one still in use).
5. Commit with explicit file paths (never `git add -A`), push, then deploy. Production data is never changed without the user's approval (`prod-run.sh --write` only then); production checks are read-only.

Local testing: the app runs with `php artisan serve --port=8001` (port 8000 is another project); the local test station's admin is `dev@local.test`. Test data goes in after `scripts/dev/local-db.sh backup` and comes out with `scripts/dev/local-db.sh restore`.

## Pump readings and shifts — rules

- **A reading belongs to a date + shift** (`pump_counter_readings.shift_id`, table `shifts`). Readings run in order of **day, then shift position, then save order** — always use the model scopes `chronological()`, `before()` and `after()` (they join `shifts`), never `orderBy('date')->orderBy('id')`. In a query with that join, qualify `pump_counter_readings.id`/`.date`.
- A reading's liters sold = its value − the reading just before it (previous shift that day, or the previous day's last shift). Adding, editing, moving (day, shift or pump) or deleting a reading recomputes the reading after it (and, when moved, the one that used to follow it). The sales of every affected reading are released **before** any is recreated, so FIFO fuel cost is drawn back in order and totals stay the same.
- A reading placed before a later one must sit **between** its neighbours (server and client check). The newest reading has no lower limit (meter replacement) — the entry table asks first.
- **Shifts** (Settings → Shifts, admins): every station has at least one; with a single active shift **no shift selector or column appears anywhere**. Positions never change: new shifts are appended, a shift with readings can only be deactivated, the last active one can't be turned off. Times are optional and **only choose the default shift** in the entry form; a night shift past midnight stays on the day it started. Readings created without a shift go to the first active one (`Shift::defaultShift()`).
- Several readings per pump in one shift are allowed (tank switch).
- **Entry table** (`pump-counters/index.tsx`, `components/pump-counters/entry-row.tsx`): inputs always start empty — saved readings are never prefilled. A pump with a reading in the selected date + shift shows a green check on its badge and (admins) a pencil linking to the edit page. A value typed for such a pump is an additional reading, after asking "هذه المضخة لها قراءة في هذه الوردية، هل تريد إضافة قراءة أخرى؟" (Cancel leaves that pump out). On past dates, pumps with nothing in that date + shift get amber inputs and the date shows a small "تاريخ سابق" badge. Validation messages show only after leaving a field or on save; counter values are shown with thousands separators (`MoneyInput`). The sales chips show liters and government liters per fuel type (each in its colour) for the entry **date + shift** — what's saved there plus what's typed and not saved yet — and hide a chip whose value is 0. Changing the entry date sets the history range below to that day (a range picked there stays until the date changes again; changing only the shift keeps it).
- **Typed values never carry over** to another date + shift. Switching with unsaved values (any reading/government/return/notes field typed) asks "لديك قراءات غير محفوظة لتاريخ …": حفظ ثم انتقال (saves to the original date + shift through the normal save questions, switches only once the save succeeded), تجاهل (clears and switches), إلغاء (stays, values kept). Leaving the page with unsaved values asks too: tab close/reload (`beforeunload`), links (`router.on('before')`, except same-page reloads with `preserveState`), and back/forward via `lib/leave-guard.ts` — that one must be installed in `app.tsx` before the router, because window `popstate` listeners run in the order they were added.
- Each row has two locked boxes (fixed width, never focused): **previous reading** — always the reading just before the selected date + shift in chronological order, never the pump's newest — and **quantity sold** (typed value − previous, red when negative, amber at 0). With nothing typed, a recorded pump shows its saved reading's previous value and liters sold. This is display only; the server computes and stores the sales. The table must fit at 1366px without horizontal scroll (root font is 18px, so rem widths run large). Headers stay on one line ("حكومي (لتر)", full text on hover); spare width goes by percentage to the five number columns and the tank, and notes is held to 18% (≈17rem at 2560px) — it must not absorb the spare space. The locked boxes fill their column (their text has no width of its own: `w-0 grow truncate`). The history table uses the same rules and fits at 1366px only just (8 columns, no spare width — don't add one without merging another): previous → value in one column ("2,591,928 ← 2,593,912", the arrow following the text direction), government / return in one, a note as an icon that opens it (`components/note-icon.tsx`), and who recorded it on hover over the time. The time is the reading's `created_at` (rule below); the rows keep the readings' own order.
- **Times shown in lists are when a record was saved** (readings history, Transactions page and export, Cash Box history): one line, `created_at` — for a fuel sale its reading's (`Transaction::savedAt()`) — e.g. "21 تشرين الأول، 02:19", the year only when it isn't the current one, plus " · الصبح" (the shift) for fuel sales and readings when more than one shift is active (`components/shown-time.tsx`). No second line, no reading date beside it. Lists sort by it (`scopeLatestShown()` in SQL, `shownSortKey()` in PHP — keep the two in step). Display only: a fuel sale's `occurred_at` is noon of its reading's date and decides the day it counts for in every total and date filter; never move it. `occurred_at` times before 2 Oct 2026 are UTC wall-clock (the station-time migration converted only `created_at`), another reason not to show them. Rows in these tables are one line and the same height.

## Amounts filled from a price

- An amount (or price per liter) the app fills from a price — Store buy/sell from the item's prices, a fuel delivery from the tank's fuel price — is filled **only in that price's own currency** (`lib/price-amount.ts`: `priceAmount()`, `refillAmount()`). Choosing another currency clears it and shows "سعر الصنف/الوقود محدد ب…" — never convert it with an exchange rate; switching back fills it again. A typed value stays while the quantity changes, but **a currency change always clears or refills it, even a typed one** (a number typed for one currency must never be saved in another). Fuel debts don't need this: their currency is locked to the fuel price's.

## Cash boxes and paying in another currency — rules

- **One box per currency.** A box's balance is the Cash Box's own sum of everything recorded up to today (`CashBoxController::summarize()`'s `net` from the start; `App\Services\CashBox::balances()`). There is no stored balance.
- **Money out** — expense/purchase transactions (create and edit, unless recorded as a debt), Store buy and its history edit, a cash advance (receivable debt with "affect cash box"), paying a debt the station owes (payment, settle, bulk settle on Debts and Debtors), and the currency given in an exchange — goes through `CashBox` (controllers use the `PaysFromCashBox` trait; forms use `CashSourceFields` + `useNegativeCashConfirm`). Sadcop transfers are always SYP and are left out.
- **Another currency than the primary one**: paid from that currency's box only if it holds enough — otherwise blocked ("رصيد صندوق … غير كافٍ") — or from the primary box at a rate the user gives ("1 USD = X SYP", pre-filled with today's saved rate). Then the record is stored **in the primary currency** (what left the box) with `original_amount/original_currency/original_rate` as information only; history shows "6,950 SYP (50 USD @ 139)". A debt payment keeps reducing the debt in its own currency; `debt_payments.cash_amount/cash_currency/cash_rate` say what left the box (`DebtPayment::cashCurrency()/cashAmount()` — use them, not the debt's currency, for anything about cash). The bulk settles only check boxes; they offer no conversion.
- **The primary box may go negative** (expenses are entered before the day's sales), but only after the user confirms: the server answers `confirm_negative_cash` with "رصيد صندوق … سيصبح سالباً … هل تريد المتابعة؟" and the form resends with the flag. Editing a record checks the box **without its own old amount** (`takenOutBy()` / the `giveBack` prop).
- **Opening cash** (`cash_box_openings`, one per currency): no longer shown anywhere (taken off the Cash Box page on 21 Oct 2026 — no station had used it; Dabaj recorded its starting cash as an Other Income entry, al-hurria none). The table, model, routes and `components/cash-box/opening-cash.tsx` remain until the owner decides on removing them. It is the cash a box held when the station started; counted by the Cash Box as money in on its date (`opening_cash` in `summarize()`, a history row) — never income, so Earnings, Statistics and the annual summary don't see it.
- Earnings are unaffected by where a Store purchase was paid from: Store profit costs each sale at the item's purchase price, not at purchase records.
- **Cash Box Excel export** (`CashBoxController::ledgerSheet()`): one row per day, every figure taken from `summarize()` for that day so the running balances end exactly on the page's. The primary currency keeps the ledger columns (Sold, Sadcop, Government, Other income, Exchanged, Expense); every other currency with anything in the sheet gets Cash Box / Income / Exchanged / Expense. Opening cash entries are rows of their own (note "Opening cash (USD) …"). Balance cells are formulas carried from the previous row.
- **Only a fuel delivery carries a tank / fuel type / liters / price per liter** (`TransactionController::withFuelFields()` clears them for every other type — the form always sends the selected tank). Label a record by its fuel only for fuel sales and deliveries; anything else by its description (older expenses still carry a fuel type: 18 on Dabaj, 2 on al-hurria as of 21 Oct 2026; their data was left as is).

## Patterns worth reusing

- **A plain `<input type="date">` picker + preserving intraday order**: when a form lets you pick just a date (no time), merge it with the current time-of-day rather than collapsing to midnight, so same-day entries still sort correctly: `Carbon::parse($data['date'])->setTimeFrom(now())`. On *update*, only re-time the record if the date actually changed to a different day — otherwise resubmitting the same date on every edit keeps bumping the timestamp and loses the original time.
- **Date-only column uniqueness checks**: `Rule::unique()` compares the raw submitted string against the stored column — but Eloquent's `'date'` cast saves a full datetime string (e.g. `"2026-08-14 00:00:00"`), so a plain `Rule::unique` check silently never matches and lets a real DB constraint violation crash through as a 500. Use a manual `whereDate('column', $value)->exists()` check in the controller instead.
- **Debts** support partial payments (`debt_payments` table, `Debt::recordPayment()`/`remainingAmount()`/`paidAmount()`); Cash Box reads cash movement from `debt_payments`, never from a debt's `amount` directly, so a partial payment shows up on the day it actually happened. Debtors can have one level of sub-debtors (`debtors.parent_id`, no grandchildren) — a parent's Debts view rolls up its children's debts too.
- **Shop** (stock items) purchases use `TransactionType::Purchase` (sales still use `OtherIncome`) — a shop transaction is distinguished from other purchases only by its nullable `shop_item_id`. `TransactionType::Purchase` is also used for Sadcop deposits; it's given the exact same cash-flow treatment as `Expense` everywhere money totals are computed (Cash Box, Statistics, Admin Earnings all `whereIn('type', [Expense, Purchase])`) — it's purely a separate label/filter category, not a different kind of money movement. `transactions.type` has no real DB-level CHECK constraint despite being declared as an `enum()` column in its original migration, so adding a new case needed no schema migration — only a data-backfill migration (`DB::table('transactions')->update(...)`) to recategorize existing rows.
- **Pumps can have multiple fuel types** (`fuel_pump_fuel_type` pivot) but share **one physical counter** — the fuel type of a sale is determined by which *tank* is picked when recording the reading, not by the pump. Don't try to give a multi-fuel pump separate counters per fuel type; that was an explicit design decision.
- Historical-record corrections (editing/deleting a past pump counter reading, inventory entry, Sadcop ledger entry, transferring a debt to another debtor) are consistently gated to `role:admin`.
- **A Radix `Popover` (e.g. `DateRangePicker`) nested inside a Radix `Dialog` will close the whole Dialog on every click inside the popover** if any two `@radix-ui/react-*` packages in `node_modules` resolve to different versions of a shared internal primitive (`react-dismissable-layer`, `react-context`, `react-focus-scope`, etc. — each is its own npm package). Different copies mean different React Context instances, so the nested Popover's dismissable layer isn't visible to the Dialog's, and the Dialog treats any click inside the portaled popover content as an outside click. `package.json`'s `overrides` block pins every shared Radix internal to one resolved version app-wide — this is the real fix; if a future `npm install`/dependency bump reintroduces a split (check with a script that walks `node_modules/@radix-ui/**` diffing versions per package name), re-pin the newest version there rather than reaching first for a component-level `onPointerDownOutside` workaround. The `Settle filtered debts` dialog in `debts/index.tsx` also keeps a small `onPointerDownOutside` guard (ignores clicks inside any `[data-radix-popper-content-wrapper]`) as a belt-and-suspenders layer, since the dedup fix couldn't be confirmed against a real browser in the session that added it — safe to remove once someone's actually clicked through it.

## Secrets

Never commit credentials to this repo or to CLAUDE.md. Production secrets (R2/Litestream, super admin credentials, etc.) are set via `fly secrets set` and are not recoverable from git history — if a secret was ever pasted into a chat/session transcript, treat it as compromised and rotate it.
